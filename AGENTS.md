# cb_site

- This repository owns the Conch's Blessing codex UI and Pages workflow. Mod definitions and translations come from the checked-out `Ba-koD/conch_blessing` source through `generate_items_js.py`.
- Preserve a focused search input across filtering. During IME composition, wait for composition completion and update only the result rows; never recreate the detail panel per keystroke.
- The filter button beside the search opens a panel of extra conditions: type, quality, item pool, stacking, golden/Mom's Box (trinkets), and features (own upgrade effect, synergies, evolution). Choices within one group widen the match, groups narrow it, and the feature group needs every chosen feature. Each option shows how many items it covers, and options no item has are left out. Like the search and the answer chips, filters only dim tiles in place, and a chip changes in place so it keeps focus; the button shows how many choices are active, and Escape closes the panel. Do not offer a REPENTOGON filter derived from EID warnings, because some items that need it do not say so in their EID.
- Synergy filters search both English/Korean names and synergy descriptions. Normalize whitespace and match every query term across those fields, including mixed name/description queries.
- Synergies are the last content section in item details, after effects, upgrade paths, facts, and link actions, on both desktop and mobile.
- Show Magic Conch origin/answer/result mappings for mod origins as well as vanilla origins. Evolution routes and their localized conditions are separate, derived only from explicit evolution statements with own-item references in source locales; neither an origin mapping nor a downgrade establishes evolution.
- Detail previews have a viewport-aware maximum height and internal scrolling, and shrink for short content on desktop and mobile. An explicitly pinned desktop item wins over hover/focus previews until unpinned or another item is selected; clicking its tile again unpins it.
- Every collectible, familiar, active and trinket detail lists whether copies stack, from the mod registry's `stackable` field (absent means it does not; actives never stack). For a trinket this counts more copies only. Golden copies and Mom's Box are a separate fact shown on every trinket (user decision 2026-10-29), because a trinket may stack yet ignore them or the reverse (Angel's Crown: only golden copies and Mom's Box change it). Its 황금·엄마의 상자 effect section, right after the effects, comes from the trinket's EID `specials`: the `append` lines in golden / Mom's Box / both order, or the effect lines with the `specials.normal` numbers multiplied x2 for golden or Mom's Box and x3 for both, as the engine's trinket multiplier does; golden and Mom's Box share one row when they read the same. Effect text drops EID icon markup, except that a `{{QualityN}}` icon stands in for its grade and becomes the digit N ("0/1등급"). Conch Pearl leaves out held items that do not stack, so this fact is how players see which ones it can still give. Cards and runes have no stacking fact.
- Vanilla item IDs, English/Korean names, and sprite paths belong in `data/vanilla_items.json`. `import_vanilla_items.py` reads extracted vanilla XML/string tables and installed enums without modifying the game files or another mod. Preserve native pixel sprites under `assets/vanilla`; do not invent Korean translations from enum names.
- `build_vanilla_js.py` validates the committed catalog/assets before export. Pages packages that export and the full vanilla asset directory. All vanilla references use their ID/type namespace to avoid collectible/trinket collisions.
- Cards and runes come from the mod's pure-data `scripts/items/cards/definitions.lua` and their `pockets.<KEY>` locale text. They are additions to the game, not Magic Conch results: show them in their own group with a how-to-get note and no upgrade path. `generate_items_js.py` crops each one's pocket-slot art (the third 32x32 frame of its sheet) into `site_pockets/`, which the Pages workflow publishes as `resources/gfx/items/pockets/`.
- The site shows only what the game plays (user decisions 2026-10-29 and 2026-10-31): an item's own presentation (a catalog row with an `effect`, `fx: "applied"`, headed 전용 강화 연출 / Own upgrade effect) or, without one, its flag's default animation (`fx: "default"`, headed 기본 강화 연출 / Default upgrade effect). Both details and the effects tab open the player with `?ingame`, which never shows a concept. The 전용 강화 연출 feature filter still counts own presentations only.
- Item details show that presentation directly through the player's compact mode (`upgrade-player.html?ingame=1&embed=1#KEY`), as its own section right after the upgrade path; it waits on a still frame and plays when pressed, never by switching to the effects tab. Each detail view (desktop panel, mobile sheet) keeps one player for good: re-renders and hover/focus previews only send it a `show` message, so it never reloads the 14 MB page or adds history entries, and the player is created lazily the first time a view shows an item with an effect. Size each small player from the height it reports, and stop a player the page hides (the sheet's when it closes, small ones when the effects tab opens, the tab's when the codex returns). Volume belongs to the player and is shared between players through localStorage.
- Search engines read static pages (user request 2026-11-05). After the Pages workflow assembles `build/`, `prerender.cjs` writes the home page with its tiles and first item in the HTML, one page per item at `items/<slug>/` (Korean) and `en/items/<slug>/` (English), `sitemap.xml`, `robots.txt`, and any ownership files from `verification/`. A slug is the item key in lower case with `_` turned into `-`. It runs `script.js` in Node with stub globals through its `CB_PRERENDER` hook, so the pages hold the codex's own markup; never write a second renderer. Each built page replaces the `<!-- seo -->` block of `index.html` (title, description, canonical, hreflang, Open Graph, JSON-LD); keep those markers and the elements the script fills, since the build fails rather than writing a page without them. Work-in-progress items get `noindex` pages and stay out of the sitemap; `robots.txt` keeps crawlers off the 14 MB `upgrade-player.html`. The site origin and meta-tag verification codes live in `seo.json`; the search-result wording is `siteName`, `metaHome` and `metaItem` in `texts.js`. Search results ask for an icon larger than 48px, so `favicon-192.png` is `favicon.ico`'s 32px art enlarged 6x nearest-neighbor; remake it whenever the icon changes. Google takes the site name and icon from the home page only.
- AI assistants and other tools that read a page as text must find every item, not only the first one (user report 2026-11-05: an assistant asked to recommend items from the home page saw Live Eye's effects only, because the tiles are pictures and only the first item's detail was in the HTML). The home page therefore carries a collapsed text list under the tiles (`#catalog`, 모든 아이템 효과 글로 보기: each released item's names, type, quality, quote, effects and upgrade path, names linking to the item page and selecting in place on a plain click); item pages leave it empty so they do not all repeat it. `prerender.cjs` also writes `llms.txt` (English index with links) and the whole detail of every item, synergies included, in `llms-full.txt` (Korean) and `en/llms-full.txt`; the home page links them in its head and in the list's note. The list and both files come from `script.js`'s `itemText`, the plain-text form of the same detail data; extend it rather than reading item data separately, and keep the files free of icon markup.
- An item page names its item and language on `<html>` (`data-page-item`, `data-page-lang`) and sets `<base>` to the site root. There the page's language is the auto choice (an explicit saved choice still wins), the page item opens without rewriting the address, and the tab title names the pinned or open item, in the same form as the page title, and falls back to the page item whenever nothing is open, so it never shows the bare site title. The page item's name is the page's `h1` (every other detail heading is `h2`). On narrow screens an item page shows its own item at the top of the page, in the panel, visible in the static HTML, instead of opening the sheet; other items still open in the sheet (user report 2026-11-07: Google, which reads pages at phone width, indexed several item pages as the bare codex with the site title and intro text, because the item was only in the hidden panel or the script's sheet). The home page keeps choosing its language from the browser, and selecting an item still writes `#KEY` without a history entry; old `#KEY` links keep working. Item links inside details are `<a class="link">` to the item's page that select in place on a plain click; Copy link gives the item's page in the current language.
- Before publishing, check generation against the current mod source, image/reference coverage, Korean composition events without input replacement, English/Korean search, desktop/mobile layout, and the Pages workflow result.
